# 证据驱动的 Agent 工作流

选择能处理真实任务形状的最小架构，并让每次状态跃迁都留下可检查的对象和证据。不要把 Prompt、Loop、Workflow、Graph 或多 Agent 当作先进度阶梯。

## 工作契约

- 先定义任务对象、完成状态、证据、权限和恢复责任，再选择架构。
- 默认先建立能力、工具和验收均足够的单 Agent 基线。只有稳定失败指向可并行分支、上下文容量、权限隔离或局部恢复，才用最小多 Agent 结构做对照。
- 法规或安全要求必须职责分离、外部副作用必须隔离，或单次任务无法安全取得单体基线时，可以豁免实跑；记录具体原因和替代证据。
- Agent 不需要先形成同一种看法。它们必须共享稳定对象 ID、来源、任务边界、证据协议、冲突裁决者、集成负责人和恢复负责人。
- 生成、构建、提交、平台记录、公开可见和外部送达是不同状态。只使用最后一个已有证据的状态词。
- 发布、发送、付款、删除、凭据处理和其他高风险或不可逆动作保留人工授权；工作流设计本身不获得执行权限。
- 文件序号、列表位置和聊天顺序不能充当对象身份。跨源稿、封面、DOCX、发布记录和回执时使用稳定 ID，并以当前哈希或外部唯一标识绑定。

## 第一步：建立工作合同

把 [workflow-contract.template.json](assets/workflow-contract.template.json) 复制到项目的 QA 或治理目录，再填写：

- 任务目标、范围、非目标、风险和负责人；
- 任务形状与架构选择信号；
- 单 Agent 基线、稳定失败与升级理由；
- 稳定对象、来源、所有者和工件映射；
- Agent 输入、输出、验收、编辑范围与集成责任；
- 本次运行要求、禁止和已验证的 Claim，以及各自证据；
- 外部动作权限、检查点、失败范围、重试和回退责任。

合同定义目标、对象、门禁、权限、恢复和执行模型；run 记录本次工件、证据、审批、失败、交接与完成声明。两者分开保存，并让 run 绑定合同修订号和规范化合同 SHA-256。

## 第二步：选择最小控制形状

完整读取 [architecture-selection-gate.md](references/architecture-selection-gate.md)，再选择：

- `prompt`：一次性、低风险、无需循环验证；
- `loop`：围绕一个主要目标重复生成、检查和修正；
- `workflow`：步骤和分支稳定，顺序与输入输出可预先定义；
- `graph`：存在动态分支、持久状态、权限交接、局部恢复或人工介入。

先修正任务合同，再升级架构。Graph 可以包含 Loop，Workflow 也可以调用 Agent；命名不替代任务形状证据。

## 第三步：用独立 Claim 约束完成

完整读取 [completion-evidence-contract.md](references/completion-evidence-contract.md)。不要把完成压成一个会被滥用的线性状态。分别验证工件已生成、工件已验收、提交被接收、目标记录存在、私密访问、公开访问和业务效果；后一项不能由前一项自动推出。

证据必须说明它证明哪个 Claim、位于哪里、状态如何，并绑定本次运行、合同修订和当前工件 SHA-256。合同或工件变化后，旧验证和旧审批立即失效。没有证据时删除 Claim 或保持未决，不用“流程跑完”补齐现实。

## 第四步：只在瓶颈成立时增加 Agent

完整读取 [multi-agent-collaboration-contract.md](references/multi-agent-collaboration-contract.md)。

涉及子任务模型选择、工位注册或迁移时，按该合同的“工位模型与运行核验”处理。模型偏好由当前有效的用户规则和部署配置管理；本 Skill 不另设模型价格表。实际模型、思考档位和权限必须从本次子任务元数据读回，不能由启动参数或工位自述推出。

1. 保存强单体基线与稳定失败；
2. 把失败归因到一个可观察瓶颈；
3. 估算并行收益、协调成本与人工审核容量；
4. 只增加解决该瓶颈所需的最小 Agent 数；
5. 让每个 Agent 交付来源、文件、测试、截图、回执或失败说明；
6. 由唯一集成负责人写入最终状态并做端到端验收。

多个 Agent 同时修改同一核心对象、每一步都依赖前一步、没有便宜的独立验收，或人工审核已经饱和时，默认保持单体或串行执行。

## 第五步：校验并执行

从 Skill 目录先做一次非严格校验，取得报告里的 `derived.contract_sha256`：

    python scripts/validate_workflow_contract.py path\to\workflow-contract.json --report-json qa\workflow-contract-draft-report.json

把该摘要写入 `run.contract_sha256`，再做严格校验：

    python scripts/validate_workflow_contract.py path\to\workflow-contract.json --report-json qa\workflow-contract-report.json --strict

合同内容改变后必须重新执行这两步，旧摘要和旧运行证据随即失效。`--strict` 会让警告也阻断。校验器只检查合同可判定部分；架构净收益、真实用户体验和高风险授权仍由明确的人类负责人判断。

执行时：

- 每个状态跃迁先满足对应证据门禁；
- 失败只重开受影响的对象和分支；
- 已验收工件保持冻结，除非上游合同改变；
- 外部结果不清时先查询真实状态，再决定是否重试；
- 新证据推翻旧规则时，更新合同、回归测试和长期规范。

## 第六步：收口与内化

结束前记录：

- 最初选择的架构与证据；
- 哪个稳定失败支持或反驳了升级；
- 当前已验证 Claim、阻断门禁与仍缺证据；
- 哪条反馈已成为可复现症状、规则或测试；
- 哪些经验应进入 Skill、工作规范、模板或确定性门禁。

只把重复出现、影响高风险状态，或能写成可观察验收条件的经验升级为长期规则。一次性偏好和只在当前文章成立的观点留在项目记录。用户明确要求跨项目制度化时，调用 `$codify-project-learnings`。

## 完成门槛

只有同时满足以下条件，才可称为工作流设计完成：

- 工作合同通过严格校验；
- 架构选择与任务形状一致；
- 多 Agent 有单体失败或明确豁免证据；
- 每个 Agent 有边界、工件、验收和集成负责人；
- 完成声明只包含已有独立证据的 Claim；
- 高风险外部动作有明确授权状态；
- 回退、失败范围和恢复负责人已记录；
- 经验内化去向和未完成项可被审计。
