# Agent 架构选择门禁

## 先描述任务形状

在命名架构前回答：

- 一次输出是否足以完成任务；
- 结果是否需要同一目标下的反复验证；
- 步骤、顺序和分支是否稳定；
- 是否存在运行时才知道的动态分支；
- 中间状态是否需要跨失败或跨会话保留；
- 是否需要权限交接、人工介入或局部恢复；
- 哪些对象可以独立验收，哪些必须共享上下文；
- 外部副作用失败后能否安全重试。

## 选择规则

### Prompt

用于一次性、低风险、无需循环验证的任务。只要结果必须反复检查、保存状态或调用高风险外部动作，就不能只靠 Prompt 承担治理。

### Loop

用于围绕一个主要目标执行“生成—检查—修正—再验收”。Loop 适合一个所有者、一个主要工件和便宜反馈。若多条分支需要独立状态与恢复，继续升级。

### Workflow

用于步骤和分支预先可知、输入输出稳定的任务。工作流的价值是固定顺序、角色与检查，不是让每一步都改由 Agent 自由决定。

### Graph

只有下列信号至少一个真实存在时才采用：

- 运行时动态分支；
- 持久状态和检查点；
- 权限或人工门禁；
- 局部失败、局部重试和恢复；
- 多种节点类型需要共享同一状态合同。

Graph 不等于多 Agent；节点可以是代码、工具、模型、Agent 或人。简单线性任务不因画成图而更可靠。

## 单体基线

默认给一个能力、工具与上下文均足够的单 Agent：

- 同一份输入；
- 同一验收标准；
- 同一风险权限；
- 明确时间、成本和质量证据。

记录稳定失败，不记录“感觉任务很复杂”。稳定失败至少说明：在哪个对象、经过什么操作、出现什么可复现偏差、哪项验收失败。

以下情况可豁免实跑，但必须记录理由、人工批准和替代证据：

- 法规或安全要求职责分离；
- 凭据、网络或数据边界不允许同一执行者持有全部权限；
- 外部副作用要求独立复核；
- 单体试验本身会造成不可接受风险。

## 升级判定

多 Agent 只针对已定位瓶颈：

- `parallelizable_branches`：可并行且低耦合的分支；
- `context_capacity`：必须隔离的信息域或上下文容量；
- `permission_separation`：职责或权限必须分开；
- `local_recovery`：分支失败需要局部恢复。

以下信号通常反对拆分：

- 多个执行者同时修改同一核心对象；
- 每一步强依赖上一环；
- 没有独立验收；
- 任务很短；
- 人工审核容量小于并行产出；
- 协调、汇总、重试和冲突成本无法估计。

最终比较净收益，而非 Agent 数量：节省的关键路径时间与新增覆盖，必须大于协调、重复读取、冲突、汇总、验证和人工审核成本。
